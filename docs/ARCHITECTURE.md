# Architecture

## Overview

```
 React UI (src/ui)  ──►  services (src/services)  ──►  Dexie / IndexedDB (src/db)
        │                       │
        │                       ├─► engines (src/engines) — pure, deterministic, no I/O, no React
        │                       ├─► import pipeline (src/import)
        │                       ├─► backup/restore (src/backup)
        │                       └─► reports (src/reports)
        └─ service worker (Workbox, generated by vite-plugin-pwa) caches the app shell for offline use
```

* **Local-first.** All data is stored in the browser’s IndexedDB (database `au-tax-ledger`). No server, account,
  telemetry or network access is required after the first load.
* **One ledger for both workspaces.** Every income, expense, trade, transfer, cash movement, fee and adjustment is a
  `Transaction` (`src/domain/types.ts`). Tax & Business and Trading views are filters over the same records, so a
  prop-firm payout entered in Trading appears in the business schedule once classified — no double entry.
* **Pure engines.** Tax and trading calculations (`src/engines`) take plain data and return plain results. They have
  a single implementation used by the UI, reports, snapshots and tests.

## Data model

Tables (IndexedDB stores): `transactions`, `accounts`, `instruments`, `rates`, `corporateActions`, `taxProfiles`,
`userProfile`, `businessProfiles`, `assets`, `logEntries`, `inventory`, `counterparties`, `categories`, `documents`,
`docBlobs`, `importBatches`, `importTemplates`, `rawRows`, `reconciliation`, `audit`, `calcRuns`, `reports`,
`backups`, `connectors`, `settings`, `meta`, `recurring`, `drafts`.

Entity coverage of the specification’s list:

| Spec entity | Where |
| --- | --- |
| User / tax / business profile | `userProfile`, `taxProfiles` (per FY), `businessProfiles` |
| Financial year | Derived (`fy` on records; `lib/dates.ts`) |
| Financial account, counterparty, instrument | `accounts`, `counterparties`, `instruments` |
| Transaction, transaction leg | `transactions` (multi-asset legs embedded: `instrumentId/quantity` + `counterInstrumentId/counterQuantity`; category splits in `splits`) |
| Trade execution, position | Trade transactions; positions derived by the derivative engine / performance module |
| Acquisition lot, disposal allocation | Derived by the lot engine; persisted inside calculation snapshots (`calcRuns.result.disposals[].allocations`) |
| Corporate action | `corporateActions` |
| Income / expense record | Transactions of kind `income` / `expense` / `fee` |
| Asset, depreciation record | `assets`; schedules derived by `depreciation.ts` and stored in snapshots |
| Currency, exchange-rate record | ISO registry + custom codes in settings; `rates` |
| Tax classification, tax-rule version | `TAX_CLASSES`, rule sets in code + imported in settings |
| Calculation run / result | `calcRuns` (immutable, with input fingerprint and rule-set id) |
| Reconciliation item | `reconciliation` |
| Import batch / template / raw source rows | `importBatches`, `importTemplates`, `rawRows` (original values kept) |
| Document | `documents` (metadata) + `docBlobs` (bytes) |
| Audit event | `audit` |
| Report snapshot, backup manifest | `reports`, `backups` |
| Future connector configuration | `connectors` |

Raw imported values are never discarded: each imported record links (`rawRowId`) to its `rawRows` entry containing
every original column, including unmapped and extra columns.

## Persistence guarantees

* **Transactions:** every multi-record write (record + audit + revision; import batch + raw rows + instruments +
  records) runs in a single IndexedDB transaction — all or nothing. Tested by forcing a failure mid-import.
* **Idempotency:** records have stable ids assigned before the first write; retrying a save updates the same record.
* **Revision counter:** `meta.revision` increments on every write; derived results (engine runs, tax years) are cached
  by revision and recomputed only when data, rates, rules or settings change.
* **Drafts:** unsaved new-record forms are stored in `drafts` and recovered after a crash.
* **Persistent storage:** the app requests `navigator.storage.persist()`; status is shown in Data health.
* **Repository boundary:** the UI never writes to Dexie tables directly for financial records; all writes go through
  `services/ledger.ts` (and the import/backup modules), so an alternative backend (e.g. encrypted sync) can be added
  behind the same functions.

## Import framework

`parse (PapaParse) → template detection (header signature) → mapping (auto-map synonyms + user edits + constants +
value maps) → prepareRows (pure: dates/time zones, numbers, sides, asset classes, fingerprints, duplicate status) →
preview (user may change per-row action) → commitImport (atomic) → rollbackImport`.

Duplicate detection: (account, source id) index for exact matches and “changed values” detection; fingerprints of
account/kind/date/time/zone/symbol/side/quantity/price/amount/currency/description **plus an occurrence counter** so
repeated identical rows inside one file stay separate while re-imports are recognised.

## Currency providers

`RateIndex` serves any loaded `RateRecord`s (imported files, manual entries, demo data). Future providers implement
the connector contract and output `RateRecord`s (with `source`, `type`, `timestamp`, `retrievedAt`) through the same
import pipeline, so provenance is uniform. The resolver distinguishes daily reference rates from execution/intraday
rates and records which was used.

## Tax-rule versioning

`RULE_SETS` are immutable objects with `id`, `version`, `status`, `sources`, `notes` and `notImplemented`. `ruleSetFor(fy)`
returns the highest version for a year (built-in or imported). Calculation snapshots and report snapshots store the
rule-set id. Importing a new version never modifies existing snapshots; the user saves a new snapshot with a reason,
and the snapshot history shows what changed.

## Offline / PWA

`vite-plugin-pwa` generates a Workbox service worker that precaches the app shell, JS/CSS, icons and sample files,
with a navigation fallback to `index.html`. `clientsClaim` makes the first visit offline-capable without a reload;
new versions prompt the user before reloading. The router uses hash URLs so any page works from the cached shell.
